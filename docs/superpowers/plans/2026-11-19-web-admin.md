# Website Admin Dashboard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/admin` pages on the website that do everything the app's Owner Dashboard does, with a sound alert for new orders.

**Architecture:** Client components using the shared browser Supabase client and the signed-in admin's session; the existing `is_admin()` row-level rules enforce access. Pure data helpers in `website/lib/admin/*` are unit-tested with a mocked client; pages are thin.

**Tech Stack:** Next.js 16, React 19, Tailwind 4, @supabase/supabase-js 2, vitest + Testing Library (happy-dom).

**Spec:** `docs/superpowers/specs/2026-11-19-web-admin-design.md`

## Global Constraints

- No database changes; no service-role key in any admin code path.
- No new dependencies.
- Admin pages: `robots: { index: false, follow: false }`.
- Status transitions offered: pending→preparing ("Accept & start cooking"), pending→cancelled ("Reject", confirm), preparing→ready ("Mark ready"), ready→completed ("Mark completed").
- Images: JPG/PNG/WebP, ≤ 5 MB, path `menu/<epoch-ms>-<clean-name>` in bucket `menu-images`.
- New ids: items `menu-<epoch-ms>`, categories `cat-<slug>-<epoch-ms>` (same as the app).
- Delivery bounds (DB check): base/per-km/min fee 0–1000, max distance >0–100 km, free threshold null or 0–100000.
- Times as `HH:MM`, sales by `Africa/Johannesburg` day.

## Review Focus

- Anonymous guest session present in the browser → treated as signed out, sign-in form shown.
- Two admins act on the same order → second click gets the DB refusal; page shows "already moved on" and reloads.
- Realtime subscription fails or drops → 30-second polling keeps the list current.
- First load must not play the alert for orders already present.
- Sound blocked until user gesture → explicit "Enable order sound" button; preference stored with try/catch.
